# Участие в разработке

Клонируйте репозиторий с подмодулями и установите зависимости по [SETUP.md](SETUP.md).
Назначение каталогов и команды очистки описаны в [структуре проекта](docs/repository-layout.md).

## Изменения

- Сохраняйте мобильные и десктопные сценарии при изменении QML.
- Проверяйте отрисовку и клики, а не только успешную компиляцию.
- Для сетевых ошибок указывайте шаги воспроизведения, версии клиента и ОС, время события и результат проверки.
- Различайте проверку на тестовом стенде и проверку реального VPN-соединения.
- Обновляя бинарную зависимость в `deploy/prebuilt-selfvps`, указывайте источник, версию, контрольную сумму и лицензию.

## Перед pull request

Запустите проверки, относящиеся к изменению, и `git diff --check`. В описании изложите проблему, новое поведение и фактически выполненные проверки.

Не включайте сборочные каталоги, установщики, сырые логи, дампы, SSH-ключи, пароли, клиентские конфигурации или личные скрипты диагностики. Для личных файлов используйте игнорируемый `.local/`; для готовых пакетов — `dist/` и GitHub Releases. Перед отправкой отчёта удалите из него секреты и персональные данные.

## Секреты

Не сохраняйте пароли VPS, токены GitHub, рабочие закрытые ключи или сетевые дампы в исходниках. Используйте защищённое хранилище приложения и локальные игнорируемые файлы для диагностики.

CI сканирует публикуемое дерево Gitleaks с дополнительным правилом для простых паролей. Локальная проверка: `gitleaks dir . --config .gitleaks.toml --redact=100 --ignore-gitleaks-allow`. Для истории используйте `gitleaks git . --redact=100`; историческая находка требует отзыва секрета, удаление файла из нового коммита его не отзывает.

Исключения в `.gitleaks.toml` добавляйте только для проверенных констант или явных примеров, с узким выражением и объяснением. Не скрывайте целиком файлы с рабочими секретами.
